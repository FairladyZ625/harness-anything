# PR、依赖集成与合并后监管

适用：任务已包含外部提交授权，需要处理多个变更、等待检查、诊断队列或完成合并后验证。具体平台操作按当前仓库治理执行；以下方法不授予发布、重写分支、修改保护或回滚权限。

## 正常集成顺序

1. 核实交付分支、当前头版本、基线、变更范围和工作树归属。目录已存在不证明基线正确；上游变化后先判断是否真的影响待集成状态。
2. 按仓库约定同步基线。变更了被验证状态才补相关验证；不要把机械变基当成无条件前置门。
3. 按仓库模板准备 PR 描述，覆盖整个变更范围、真实证据和剩余风险。草稿是否合适取决于交付阶段；若等待合并，核实平台是否因草稿状态而不受理。
4. 读取自动评审的具体发现，核实后修复、驳回、延期或标阻塞。它是输入，不自动替代独立批准，也不要求无穷等待二次背书。
5. 核实实际待合入状态的必需检查与有效批准，按已有队列或合并策略执行。单个 PR 也不自动获得绕队列权限。
6. 合并命令即使报错，也先回读 PR 状态、合并版本和目标分支，再决定是否重试；避免重复副作用。
7. 按契约完成台账和已授权清理。清理前核实目录无其他在飞执行、无未交接变更；只处理自己拥有的分支与工作树。

## 检查没有报告，不等于通过

监视器必须区分：尚未注册检查、待执行、执行中、失败、成功、跳过、取消，以及等待一个尚未出现的必需检查。零条检查不等于全绿；最新一次跳过也不自动抹去同一版本上先前的失败。

绑定具体头版本、事件和检查集合，不只看最新运行或一个总状态。主干前移导致的取消、定时矩阵的失败、当前合并引入的失败要分别记录。监视器不支持这些区分时，改用现有可提供完整信息的接口核实，不能把它的退出码当完整结论。

## 队列阻塞的诊断顺序

同一 PR 重复入队仍无进展时，主控接管排程层诊断，不让执行者机械重试。

| 顺序 | 核对对象 | 下一步判断 |
| --- | --- | --- |
| 1 | PR 当前头、目标分支、草稿状态、文本冲突、已有检查 | 是 PR 本身尚未满足条件，还是队列观测不一致？ |
| 2 | 平台合并状态与必需检查名称 | 等待中的检查是尚未报告，还是已删除、重命名、过滤跳过？不能仅凭等待就断定永远不会报告 |
| 3 | 队列机器人详细输出或退队原因 | 区分条件不满足、旧运行残留、认证失败、资源不足与调度故障 |
| 4 | 所有实际生效的保护与队列来源 | 可能包括分支保护、仓库和组织规则、队列条件；读不到的来源标未知，不用旧清单兜底 |
| 5 | 队列验证的组合版本及事件输入 | PR 本体绿不等于队列组合绿；是否存在旧版本或旧 PR 描述参与判定？ |
| 6 | 仓库检查声明与实际产生的名称、过滤条件 | 名称、矩阵后缀、触发条件不一致可能产生永久等待 |

同一源码版本上多个运行互相矛盾时，先查看事件载荷与平台采用规则。重跑可能重放旧载荷，不一定采用新描述。是否刷新、重排、生成新版本或重开 PR，按诊断证据和既有授权选择；这些不是通用首选修法。

不得为了合入而删除保护、忽略错误或擅自增大门禁阈值。需要改治理时走该仓授权路径。排障工具取数失败必须报告缺失来源，不能用硬编码旧数据冒充当前事实。

## 更换必需检查

仅在明确授权的治理任务中处理。先列出现有生产者、消费者与全部生效约束。让新检查实际报告并验证，再协调切换依赖它的规则；移除旧生产者前确认已无生效规则等待它。整个过渡不能制造既无法报告旧检查、又要求旧检查通过的状态。

新检查尚未存在的版本不能被提前要求报告它。具体分步与部署顺序依仓库和平台能力制定，不能照抄固定的“两次 PR”配方。保留每一步的实际报告作为证据，不削弱其他保护。

## 多个依赖变更

独立变更优先使用仓库已有队列，不为了数量多而强制连成一条链。只有真实依赖、上游语义稳定、平台和仓库允许时才叠列：

- 每层保留独立目标、变更归属和评审范围；记录其真实上游分支及上游边界版本。
- 派工前验证工作树确实包含所需上游，不能把“创建失败，目录已存在”当作准备成功。
- 验证要覆盖真正会合入的组合；各层独立通过不能证明组合通过。
- 上游被变基或重写后，只搬运下游自己的变更。先核实边界，再选择操作；不要盲目重放旧上游提交。
- 修复放在实际引入问题的层，确保每个将独立落主干的状态都有其所需证据。
- 合并后核实下游目标分支是否实际更新，不假定平台一定自动改写；基线改变后重算依赖基线的统计与证据。
- 仅在有权限且确认不再消费时取消旧验证，不能取消别人的有效 CI。

快进、合并提交、压缩合并产生不同的版本关系。不能从一次快进叠列经验推出“列尾绿就可批量合入”或改变用户合并策略。批量落地只有在仓库明确支持、全部审查和检查契约仍满足时才考虑。

## 合并后出现失败

合并后若还有契约规定的检查，记录对应版本、运行和响应负责人。区分“已合并”与“验尾完成”，不能前者完成后就丢掉后续责任。

1. 确认失败属于该版本，而不是被后续版本取代的取消或无关定时运行。
2. 对已知不稳定项也核对本次症状，不能只凭名称就忽略。保留发生记录和实际处理负责人。
3. 未解释失败作为回归嫌疑，比较最早失败版本与之前可用版本；必要时按合并序列缩小范围。
4. 暂停会扩大问题的相关动作；是否冻结所有合并、修复时限、回滚、隔离检查均由仓库既有策略与授权决定。
5. 核实修复或回滚后的状态，完成相应记录和监管交接。不把“主干已经红了”当成继续叠加未知失败的理由。
