# 让 Agent 迭代自己的 CEO Skill

这份教程面向使用者。它说明什么时候应该请 Agent 改进自己的 CEO Skill、怎样保留公共包升级，以及如何用行为证据判断改动真的有用。维护规则的唯一权威是[维护方法](maintenance.md)；本教程只负责把那套方法变成一次可执行的用户流程。

## 什么时候该迭代

把一次摩擦当作观察，把第二次同类摩擦当作迭代信号。常见信号有：

- 同一种判断需要你第二次纠正，例如 Agent 又一次为已获授权的可逆文档动作请求确认。
- Agent 反复被同一个工具或门拒绝，且每次都靠改写提示词绕过。
- 正文找不到你经常要用的规则，或者要翻很多段才能找到下一步。
- 同一原则在主文档和多个参考中出现，修改一处后另一处仍然说旧话。

一次孤立、尚未确认根因的失败先记录观察，不要马上把它写成公共规则。先确认它是通用判断、用户自己的约定、项目事实，还是工具问题；维护方法决定了不同归宿。

## 怎么开口

你可以直接对 Agent 说：

```text
把刚才这个问题沉淀进我的 CEO Skill。先区分工具缺陷、我的工作区事实和通用方法，再给出最小改动和验证场景。
```

```text
对我的 CEO Skill 做一次熵审计：检查正文预算、主文档与 references 的重复和死链；先列删除/合并/下沉清单，再改文件。
```

```text
这类摩擦已经第二次出现。请回读原场景，找应该被改写的旧规则；如果工具能从根源保证，就改工具而不要新增“记得……”规则。
```

收到请求后，Agent 应按这个顺序工作：

1. 回读任务、当前生效的 CEO Skill、相关 reference 和本次失败的事实；把事实与猜测分开。
2. 搜索同一机制的其他落点，确认这是重复问题还是一次性事件，并检查所有消费方和链接。
3. 先列删除、改写、下沉和工具修复候选。正文预算与腾位规则见[精简保护读者注意力](maintenance.md#改写然后验证)。
4. 选择一个权威落点：每次编排都要用的判断骨架留在 `SKILL.md`，特定场景的细节放进 reference，用户事实放在用户自己的记录，能由命令面保证的行为修工具。
5. 用修改前后都能复现的场景验证，然后回读原场景确认临时绕行建议已撤销。

## 从公共包派生副本

公共 `harness-ceo` 包是方法模板，不是你的历史记录。将它复制或 fork 到宿主支持的**用户拥有的技能目录或用户自己的仓库**，让该副本成为实际发现到的版本；保留公共包作为上游来源，不在上游目录直接写个人内容。不同宿主的技能目录名称可能不同，关键是目录中保留完整的 `SKILL.md`、`references/` 和 `assets/` 结构。

升级时先取得公共包的新版本，再把你的本地改动重新应用到新版本，逐条解决冲突并重跑链接检查。公共更新只应改变跨项目的方法和模板；你的工作区记录、模型观察、本地拓扑、事故、审批习惯和模型偏好留在用户自己的上下文或记录系统。不要把它们复制进公开包，也不要为了保留个人规则而冻结公共方法的错误表述。

可以用下面的边界来判断内容放哪：

| 内容 | 公共包 | 个人副本或工作区记录 |
| --- | --- | --- |
| 跨项目仍成立的判断、委托骨架、验收方法 | 保留在 `SKILL.md` 或带触发条件的 reference | 只在需要时覆盖或补充适配说明 |
| 某个项目的路径、队列、审批和交付约定 | 不写入 | 工作区治理和任务记录 |
| 你的模型表现、工具版本、模型偏好 | 不写入 | 用户模型矩阵或运行记录 |
| 某次事故的原文和日期 | 不写入 | 观察、证据和问题记录；只提炼通用机制 |

## 一次完整的迭代示例

**场景。** 一个 Agent 连续两次把只有一个文件、验收条件明确的小改动拆给多个执行者，产生了重复上下文和多余的集成步骤；用户两次都指出这类改动直接完成更快。重复出现说明当前委托规则没有帮 Agent 比较收益和协调成本。

**先取证。** Agent 回读两次任务和当前技能，确认两次工作都很小、没有独立结果，也没有需要隔离的风险。它检查可用命令和工作区约定后，判断“是否值得拆分”取决于任务的独立性、上下文隔离和复核收益，不能由命令稳定推断；因此没有工具修复项。当前正文里“任务复杂时考虑委托”过于宽泛，应改写为按独立工作、隔离或第二视角带来的收益是否高于派工与集成成本来判断。

**改写与下沉。** Agent 将这条高频判断并入 `SKILL.md` 的派工规则，合并并删除原来过宽的表述。具体如何比较多条工作线、什么情况值得增加指挥层只在拆解任务时需要，留在 `references/management.md`；正文的条件指针写明“多条候选工作线收益接近协调成本时，读带队判断的拆分方法”。移动之前，它确认该 reference 确实包含可执行的比较步骤，而不是只有标题或结论。

**验证。** 用修改前后两个场景对照：单文件、验收明确的小改动应直接完成；三个互相独立且能分别验收的结果仍应拆分并指定集成人。Agent 再搜索主文档与所有参考资料，确认“什么时候拆”只有一个权威说明，指针会把人带到细节。若小任务仍被重复拆分，回到原场景找规则表达或执行判断的问题，不再追加相似提醒。

这个例子中，通用判断被改写进主文档，场景细节下沉到参考，工具则因无法稳定推断任务独立性而不改。若另一个问题可以由工具确定性地消除，维护流程应选择改工具并删除相应提醒。迭代的产物不是更长的 Skill，而是下一次遇到同一场景时更短的正确路径。

## 如何验证改得更好

验证行为变化，不验证字数变化。至少保留一个修改前会失败或产生摩擦、修改后应正确的场景，再加一个不应被改变的邻近场景：

| 场景 | 修改前记录 | 修改后期待 |
| --- | --- | --- |
| 原始摩擦再次出现 | Agent 重复询问、被同一工具拒绝，或找不到规则 | Agent 直接走新规则、条件 reference 或工具通道 |
| 邻近的正确用法 | 原本已经能完成 | 仍能完成，权限范围和用户约定没有扩大 |

运行受影响的链接、元数据和文档检查；需要时让不了解这次事故的读者只给场景和公共包，观察他是否能找到正确落点。把未验证的解释标出来，把实际结果和证据链接写入任务记录。一次绿灯只证明这两个场景，不证明所有编排都变好；相同机制再次出现时继续回到维护方法做改写、下沉或工具修复。
