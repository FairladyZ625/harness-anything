# 决策写法

决策首先写给裁决者：他必须先看清“到底要我裁什么”，然后才检查证据。把裁决、理由和
交付工作分开放，三个读者任务才不会挤在一段话里。

## Chosen

每个 `chosen[].text` 只写一句裁决者能直接答“行/不行”的话。它回答 decision question，
不在这里证明答案，也不在这里展开实施计划。

一次决策可以合法地同时敲定多个并列判断。多条 chosen 正是复杂决策的出口：三个判断就写成
三个 `--chosen`，不要把它们压缩成一句更密的话，也不要按合计长度惩罚拆分。

每条上限为 120 个 Unicode 字符。2026-07-25 回测了 503 份决策、625 条 chosen：
P25 为 113 字，中位数为 193 字，超过 120 字的存量有 453 条。因此历史分布证明的是
存量债务，不是可读目标。两条经人确认可读的正例分别为 59 和 103 字；120 同时放行它们并
留有余量，同时拒绝已经确认难读的 501 字和 722 字段落。

正例（`dec_01KYCF5V2FRM90QV68BC45JMJX`，59 字）：

> 守卫那条「必须是 generic」是重构没做完的残留,应当去掉;把关交给紧随其后的内容比对检查(它已包含通道适配器)。

不应塞在一条里的形状（`dec_01KYCA4Q2MZNHX4N8T3K06JG02` CH1，722 字，以下为节选）：

> 三条:(1)每条性质判据必须有常驻执行者,不是审计项目……;(2)存量清零追不上腐烂流量是算术问题不是执行力问题……;(3)远程线按参与者可追责性分两级……

后者包含三个可以独立裁决的判断，完整论证应回到 body 与 task，并拆成三条 chosen。

## Body

Body 解释为什么选这个判断。证据、权衡、反对方案、风险和范围排除都放这里。这样裁决者可以
先回答“是不是这个结论”，再检查论证是否站得住。

把理由移出 chosen 不是删信息，而是恢复阅读顺序：先看裁决，再看证明。

## Task

Task 承接实施要求：改哪些文件、迁移步骤、测试、阴阳性对照、上线顺序和完成门。这些工作由
决策派生，但不是裁决者此刻要批准的那句话。

如果 chosen 同时写“裁什么”和“具体怎么交付”，实施中发现的新事实就会看起来像在修改决策。
把交付工作放进 task，才能让裁决稳定、计划可演化。

## 超限后怎么改

`ha decision propose` 拒绝某条 chosen 时：

1. 圈出其中每个可以独立答行/不行的判断，各写成一条 `--chosen`。
2. 把“因为”、对比、权衡和证据移进 `--body` 或 `--body-file`。
3. 把命令、文件修改、测试义务、发布步骤和交付条件移进 task。
4. 单独重读每条 chosen；裁决者不应先解码实施计划，才能回答行或不行。
