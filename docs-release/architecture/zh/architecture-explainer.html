这个项目是什么，解决什么问题，怎么用

先把「项目是什么」讲清楚，再讲架构。如果你只读两屏，读这一节和下面那张图。

它解决的问题：agent 记不住自己为什么这么做

AI agent 极其擅长做事，却极其不擅长记住自己为什么这么做。给它一个真实任务，它会在一次会话里产生一条 密集的推理轨迹——为什么选这个方案、做到哪一步、沿途观察到了什么。会话一结束，这条轨迹几乎全部蒸发。 下一个 agent，或者一周后的你自己，只能从零开始：决策被悄悄重新讨论一遍，工作被重做， 而且整件事无法审计，因为根本不存在可审计的工件，只有一堵没人会完整重放的对话墙。

Harness Anything 是 AI agent 的问责层（accountability layer）。它的赌注不是「做更好的笔记」， 而是把那条推理轨迹提升为活在 git 里的结构化实体：选择变成一个 decision， 可以被提议、被接受、日后被推翻，但不能被抹掉；进度变成一个 task，在既定状态之间流转， done 被完成门锁住；观察变成一个 fact，不可变、自带来源。 它们都是版本控制下的纯 Markdown，可以 diff、可以在 PR 里评审、可以长期留存。

它给谁用：给那些在用 AI agent 真干活、并且吃过「工作记不住自己」这个亏的人和团队—— 决策不知去向、「完成」其实没完、上下文撑不过一次交接。也给 agent 自己用： ha --help 能发现的命令面就是全部合法动作，凡是承重的动作，没有一个不能从这里触达。

日常怎么用：CLI、GUI 与 daemon 各扮演什么

CLI（ha）是主要入口，人和 agent 敲的是同一套命令。 它自己不持有任何真相，只把命令翻译成协议调用递给 daemon。 daemon 是真正干活的那个进程：它按仓库持有唯一的串行写者，做授权判定、冻结写计划、 追加事件、落盘文件、维护投影、拉起 agent 运行时。它在需要时会被 CLI 自动拉起。 GUI 是同一份数据之上的另一个交付面——Electron 应用，走 IPC 桥接到同一个本地 daemon， 看的是同一条读路，没有第二个真相来源。

三者的分工可以一句话记住：CLI 与 GUI 提出请求，daemon 做出判断并持有写权威，git 保存结果。

一个 task 的一生

典型的一轮是这样的：你先用 ha fact record 记下一条可复核的观察， 再用 ha decision create 立一个决策，决策里的每条主张必须用一条边指向那条 fact 作为证据——没有这条边，决策无法被接受。决策派生出 task（derives 关系）， task 由 preset 编译出整个任务包。执行时可以 ha runtime dispatch 派一个 agent 去做， daemon 拉起进程、把会话生命周期写进台账、把输出写进本地流。

收口时先 ha task submit 提交一轮 execution，包含六个字段：完成声明、交付物、证据引用、 验证说明、已知缺口、残余风险。然后 ha task review 由 reviewer 记录已核对的证据与理由， approved 才能继续。最后 ha task complete 解析这个 task 的 preset/profile 声明的确定性门， 不过就拒绝。收口时至少产出一条新的 fact，它又成为下一个决策的证据——这就是回环。

01

包与依赖方向

交付面向内依赖 daemon 的协议契约；kernel 持有领域契约、端口、存储与投影；适配器很薄，而且只有两个。

这张图在讲什么

它回答一个很具体的问题：谁允许 import 谁。整个仓库是一个 npm workspaces monorepo， 八个真实存在的工作区包排成六层。方向永远是自上而下：交付面（CLI 与 GUI）依赖协议契约，协议契约之下是 宿主与串行写者，再之下是领域服务与编译器，最底下是 kernel 与适配器。没有任何一条边往回指。

为什么这样设计

因为这个系统的核心主张是「每一次承重写入都必须经过同一条路」。要让这个主张成立，交付面就不能持有写能力， 只能持有提出请求的能力。所以 CLI 不是一个「会写 Markdown 的程序」，而是一个把命令翻译成协议调用的 客户端；GUI 也一样。真正决定写什么、以什么顺序写、能不能写的判断，全部下沉到 daemon 进程里的 RepoCell 与 kernel。这条约束在代码里是可验证的：packages/cli/src 下没有任何对 packages/application 或 packages/kernel 的 import。

读者最常误解的点

第一个误解是「GUI 和 daemon 互相依赖」。实际上依赖是单向的：GUI 的文件 import 了 daemon 的协议契约类型， daemon 侧则没有任何对 GUI 注册表的 import。图上那条蓝色的「类型依赖」边只往一个方向走。

第二个误解是把架构模型里画出来的包当成真实存在的包。当前工作区里只有 local 与 multica 两个适配器；GitHub Issues 与 Linear 适配器、独立的 daemon 客户端包、独立的契约包、 VS Code 扩展——都不存在。它们是撰写出来的意图，不是实现。第 10 章会把这几条差异逐条列出来。

第三个误解是「端口层什么都能干」。端口是被刻意收窄的：授权、artifact 读取、模板与 VCS 被导出， 而 artifact 的写入口被明确不导出——因为写只能走单写路。

这一章只说清了静态的依赖方向。下一章把同一批方框换成动态视角：一次写入沿着这些边具体发生了什么， 以及为什么读路可以整个删掉重建。

02

单写路与可重建读路

所谓 WriteCoordinator 不是一个类名，而是 RepoCell 的锁与串行队列，加上 CanonicalEventStore 的发布流水线。

这两张图在讲什么

图 2A 是一次写入的完整旅程：客户端发请求 → 协议校验 → 找到是哪个仓库并取锁 → 进入该仓库唯一的串行队列 → 判定这是什么命令并冻结一份写计划 → 追加进事件存储 → 落成 Git 对象与工作区文件。 图 2B 是读取：投影（projection，从事件账本派生出来的 SQLite 读模型）由 canonical 事件重放而成， 读查询只从投影取数，再以类型化 DTO 返回交付面。

为什么这样设计

关键是写计划先于写入被冻结。write-chain.contract.ts 要求在追加之前就声明清楚： 要写哪些目标路径、实体身份是什么、基于哪个修订号、这次操作的 id 是什么。这不是形式主义——它让「这次写入 到底改了什么」在事件被追加之前就是已知的，于是回执、幂等、恢复对账三件事都有了依据。 而 RepoCell 的串行尾保证了同一仓库同一时刻只有一个写者在推进，写者代际（writer generation）保证陈旧的写者 不会在被换掉之后还偷偷追加。

读者最常误解的点

「canonical」不等于「立刻落到 Git」。本地 WAL（write-ahead log，预写日志）是先持久的那一层； Git ref 与撰写好的文件是已落定的发布。两者之间存在一个窗口期，读取时会把 WAL 与 Git 合并起来看， 所以你不会读到「刚写完却查不到」的中间态。

SQLite 是可丢弃的。它不是第二个真相来源。删掉缓存目录下的 task.sqlite， 系统会追平（catch-up）或整表重建；正确性不依赖这个文件存活。

「一条路」不等于「一个处理器」。task、decision、fact、通用实体、runtime、文档、schedule 在追加之前各有各的处理器，它们只是在 RepoCell 与事件存储处汇合。这个分叉正是第 4 章要展开的东西。

和上一章怎么衔接

第 1 章的静态依赖边，在这里变成了一条有顺序的流水线：交付面 → 协议 → 宿主 → 服务 → kernel 存储。 接下来第 3 章把注意力从「写入怎么走」转到「被写的东西是什么」。

实体身份、事件模式与落地形态

注册表里有 12 种实体类型。按编排方式它们分成三类：有专用事件族的、走通用实体存储的、以及台账定义加运行期落地的。

这张图在讲什么

注册表 entity-kind-registry.ts 里登记了 12 种实体类型：task、fact、decision、agent、squad、 policy、execution、review、runtime-session、schedule、settings、person。每种类型在注册表里声明三件事： 它的事件族（schema，事件的模式名与版本）、它的落地位置（residency，状态存在台账里还是本地）、 以及它的撰写方式（authoring）。图上按这三个声明把它们分成了三组。

为什么这样设计

不是所有实体都值得有自己的事件族。task、fact、decision 是产品的三个知识原语，它们有各自的生命周期、 各自的文档形态、各自的审阅路径，所以每种都配了专用事件模式（task-event/v1、 fact-event/v1、decision-event/v1）。agent 与 squad 只是被存起来的配置对象， 用一套通用的 entity-event/v1 加 JSON 文档就够了，没必要复制三份基础设施。 runtime-session 与 schedule 则天生是混合的：身份与生命周期属于台账，进程与输出属于本地。

读者最常误解的点

最大的一个误解是「fact 属于 task」。当前代码里 fact 是一等实体：身份是 fact/{id}， 落成独立的 facts/{id}.md，taskId 只是一个可选的来源字段，不是身份的一部分。 早期的架构文本仍写着「fact 由 task 拥有、没有独立文件」，那是已经过时的表述，第 10 章按漂移登记。

第二个误解是「关系（relation）也是一种事件」。没有独立的关系事件族。关系是内嵌在来源实体事件里的 类型化记录，由关系图投影按规范方向与确定性 id算成图表行。所以关系不能凭空创建， 只能随一次实体写入产生——这正是「回环」纪律能被机械保证的原因。

和上一章怎么衔接

第 2 章说所有写入汇入同一个存储；这一章说明汇入的东西被分成了几种模式。第 4 章接着问一个更尖锐的问题： 既然模式已经统一声明了，为什么执行路径还没有完全统一？

通用 action 契约：已声明，执行只统一了一半

ActionEnvelope 与动作目录声明了一个共同的控制面。当前分派证明 task 生命周期与通用实体存储确实走了它，而 Decision 与 Fact 仍然分叉到专用文件。

这张图在讲什么

上面一层是已经声明好的东西：ActionEnvelope 定义了一个动作的通用外壳——kind、target、actor、 authorizationRef、idempotencyKey、actionId、version；注册表声明了每种类型的事件族与动作目录； AuthorizationPort 定义了命令边界上的策略判定点。中间是实际的分派开关， 它按 action.kind 决定交给哪一族处理器。下面是当前真实存在的四条执行路径。

为什么这样设计

先声明一个统一的控制面，再逐步把各个分支迁进来，这是有意的顺序。信封（envelope）里那几个字段不是装饰： idempotencyKey 让同一个动作被重放时不会写两遍，authorizationRef 让「谁批准的」 成为写入本身的一部分而不是外挂日志，version 让契约可以演进。这些性质一旦由通用层统一提供， 每个新实体类型就不必自己再实现一遍。

诚实标记 · 进行中

通用 action catalog 已经声明，但 Decision 与 Fact 的执行今天并没有完全走它。 Task 生命周期解析确实使用生命周期动作目录来驱动状态迁移，Agent / Squad 确实走通用的 createEntityStore；而 decision-actions.ts 与 fact-actions.ts 各自用 compileDecisionWrite / compileFactWrite 加服务追加的方式实现， ActionEnvelope 不是它们的执行权威。这是当前代码的实测缺口，也是第 9 章 Phase 6 的第一批收敛目标。

读者最常误解的点

「已经有通用契约了」经常被读成「已经通用了」。契约存在与契约被走，是两件事——这个仓库自己把它称为 采用律：一项能力只有成为唯一合法路径时才算被采用，只要还存在绕开它的近路，就一定会被绕开。 图上那两条橙色虚线画的正是这条近路本身。

另一个误解是把这条缺口当成 bug。它不是 bug——四条路径最终都追加进同一个事件存储，写入的正确性并不受影响； 受影响的是一致性成本：每加一种实体，专用分支就要复制一遍授权、幂等与撰写逻辑。

05

runtime 派工：一份 canonical 会话，加一条本地进程流

daemon 拉起供应商特定的进程，把生命周期写进台账，把输出写进本地 JSONL，并提供基于游标的 attach。终端会话是另一套宿主。

这张图在讲什么

当你让系统「派一个 agent 去做这个 task」时，发生的事情是：先从运行时实例注册表取到这个供应商 （当前支持 claude、codex、agy 三类）的配置、安装位置与认证方式，由启动编译器算出具体的 argv 与环境变量； RuntimeSpawner 检查授权、分配 dispatchId 与 sessionId、拉起进程。然后信息流一分为二： 生命周期事件进 canonical 台账，进程输出进本地的派工 JSONL 与实时流中枢。

为什么这样设计

因为这两种信息的性质完全不同。「某个 agent 在某个时刻被派去做某个 task，结果是成功还是失败」—— 这是需要长期审计、需要跨节点一致、需要能被 review 引用的事实，必须进台账。 而「进程第 4,132 行输出了什么字符」——这是高频、体量大、只对当下这台机器上正在看的人有意义的 传输数据，进台账只会把账本撑爆。所以前者是 agent-runtime-event/v1 事件， 后者是 runtime-dispatch-stream/v1 的本地 JSONL 加一个带游标的流中枢。

读者最常误解的点

「日志在 git 里」是错的。台账里有的是会话生命周期，不是输出正文。想看输出要走 attach：流中枢支持游标 attach、断流信号与 witness，客户端断开重连不会静默丢帧，而是拿到一个明确的 gap 信号。

daemon 崩了不等于派工丢了。重启接管会重新打开仍然活跃的进程与派工记录， 并把已经持久下来的输出灌回流中枢；派工结算负责写结果事件、归档报告、关闭本地记录。 联合读取则把投影里的会话与本地 JSONL 拼在一起，实在都没有时用撰写好的归档作兜底证据。

终端会话不是派工。TerminalHost 走的是直连 PTY / tmux，是另一种会话类型， 不产生派工记录，别把两者混为一谈。

任务包与文档写入：两条通道，一套落盘

新建任务包从编译好的文档出发，doc-sync 从工作区 diff 出发。两者都必须先产出事件与精确写计划，才能进入共同的发布与物化机制。

这张图在讲什么

系统里有两种把文档写进仓库的方式，它们的起点完全相反。 左边：你说「创建一个任务」，preset 编译器根据选中的 preset 编译出整个任务包——文档、二进制块、元数据， 外加一份冻结写计划，一次 canonical 操作把它整体落下。 右边：你直接用编辑器改了工作区里一份已登记的文档，候选扫描器发现了这个 diff，裁定环节判断这次改动 该被接受、拒绝，还是标成冲突。

为什么这样设计

因为「人和 agent 就是会直接改文件」是一个必须承认的现实。如果唯一的写入方式是命令，那么手改就成了 一条绕开门禁的近路；而如果手改被无条件接受，账本就失去意义。doc-sync 的做法是把手改纳入同一条路： 它带着期望基线（expected base）与归属信息进入裁定，通过之后仍然要编译成 doc-event/v1 加一份精确写计划，再走同一套发布与物化。手改因此不是例外，而是一种被治理的输入。

读者最常误解的点

裁定不是「自动合并」。decideDocWrite 的三个出口里有一个是 conflict， 它会显式停下来，而不是猜一个结果。归属与期望基线对不上，写入就被拒。

路由决定目标位置，不是你指定的路径。文档事件编译器按路由注册表算出目标； 写计划里声明的目标才是最终会被物化的位置。这也是为什么提交时不加路径限定会把当前全部 符合条件的候选一起提交——候选集合是扫描出来的，不是你手选的。

canonical ref 与 authored 分支是一起推进的。不存在「事件写了但文件没变」的稳定状态； 如果落盘中途被打断，恢复流程会对账，而不是留下半个写入。

07

fleet 拓扑：写权威留在中心

边缘节点镜像 canonical 切面、把带 claim 的命令提交给中心、把分歧文档显式暂存。写者 epoch 围住陈旧中心，schedule 的 occurrence claim 防止重复派工。

这张图在讲什么

目标形态是一个 fleet center 加多个边缘节点，共用同一份 canonical 台账。边缘持有只读副本： 它接收快照与增量帧、维护当前指针与两个 cut，但永远不是独立写权威。 边缘要写，就把带 claim 的命令通过线上契约提交给中心，中心校验后执行，边缘拿到回执再拉取新副本。

为什么这样设计

因为这是唯一能在「多节点」和「单写路」之间同时成立的形状。任何允许边缘本地写、事后再合并的设计， 都会把冲突推到合并时刻，而合并时刻没有足够的上下文做正确判断。把写权威集中在中心，代价是延迟， 换来的是顺序是确定的——而这正是账本的全部价值所在。

两种围栏解决的是两个不同问题

写者 epoch（writer epoch）是一个单调递增的中心代际，用来挡住「旧中心还活着并且还在追加」 这种脑裂情形。occurrence claim是定时任务的并发主体：一次 occurrence 带着 occurrenceId、claimFence、nodeId，只会被一个节点认领成功， canonical claim 事件先于运行时拉起。别把它们当成同一个机制。

读者最常误解的点

最常见的错误设计是「给定时审计绑一个常设 task，每次运行都写它的包」。五个边缘节点在同一分钟触发， 就会同时去抢那个 task 的租约，然后炸。正确的并发主体是 schedule 的 occurrence claim， 产出应该归属于这次 occurrence，而不是一个共享 task。这个反例值得记住，因为它是设计新写路时最容易踩的坑： 动手前先问「多个边缘节点同时做这件事会怎样」。

另一个误解是「文档冲突会自动解决」。三方暂存拿的是基线 / 本地 / 中心三份，分歧被显式暂存成一个需要处理的 出口，不会静默选一边。

进行中 · 未合入的对照

有一条尚未合入主干的分支引入了迁移用的 ledgerEpoch 并触发投影重建。它不是 当前主干上的模块，因此本图没有为它画方框。它与主干已有的写者 epoch 围栏是两个不同的机制， 不要混用同一个名字来理解。

门禁：既是策略，也是自动化，还是 canonical 证据

门禁 manifest 是唯一注册表，workflow 执行它声明的生产面，主分支产物可以被摄入成 canonical 事件，任务收口时再对账它声明的那扇门。

这张图在讲什么

门（gate）在这个系统里出现三次，图上从左到右就是这三次。 第一次是策略：tools/gate-manifest.json 是唯一注册表，58 个条目，其中 3 个聚合门、 49 个确定性门、52 个在 PR 上必过。 第二次是自动化：包脚本面按 manifest 选门（check 选 45 条、check:pr 选 44 条）， CI 工作流跑同一份策略，分支保护声明 17 个必过上下文。 第三次是证据：CI 的运行结果可以按 ci-run-observation/v1 被摄入成 canonical 事件， 任务收口时那扇 id 为 ci 的完成门就有东西可查。

为什么这样设计

因为「门存在」和「门被执行」和「门的结果是可复核的」是三个独立的性质，缺一不可。 只有第一条，门就是一张贴在路边的告示牌；有前两条而没有第三条，你就只能相信有人跑过了； 三条都有，`done` 才真的意味着 done。整个产品的一句话主张——「你的 agent 说做完了，让它拿出证据」—— 在架构上就落在这张图里。

读者最常误解的点

门默认关闭（fail-closed）。证据不足或检查未通过，结果是这次写入被拒绝， 不是被放行加一条警告。这是刻意的：只要拒绝可以被降级成警告，它就会被降级。

摄入不是自动 join。CI 产物的拉取与摄入只在主分支上做，而且是去重后追加； 任务收口门读的是包判定（passed 或 not_applicable），它不会自动跑去把某次 CI 观察事件 关联到这个任务上。想让证据算数，就得显式把它交上来。

确定性门与聚合门不一样。确定性门是可机械判定的；聚合门是若干门的汇总口。 把两者混在一起数，会得出错误的「必过门数量」。

和上一章怎么衔接

前七章讲的是机制怎么运转，这一章讲的是什么东西有权说「不行」。 第 9 章则是唯一一章讲还没做的事。

权威收敛与模型漂移

撰写出来的架构模型是经过评审的意图，快照是派生证据，而这一页的现状描述由代码决定。漂移应当在评审后回改模型，绝不在这里被静默抹平。

这张图在讲什么

系统里存在三种「架构说法」，它们的权威级别不同： 撰写的意图（架构 manifest、SSoT 文档、关键流程、LikeC4 模型）是经过评审的设计意图； 派生快照（比如从 import 关系扫出来的图）是证据，不能反过来覆盖意图； 当前代码是这一页现状描述的唯一依据。三者不一致时，本页按代码画图，并把差异登记成漂移。

为什么这样设计

因为两种反向做法都会坏事。若以模型为准，文档就会长期描述一个不存在的系统，读者按它去改代码会踩空。 若让快照自动覆盖模型，那么任何一次临时的、错误的实现都会立刻被追认成「架构」，评审就失去了意义。 折中是：代码决定现状，模型保留意图，差异显式登记，晋升必须经过人的评审。本页不做自动同步。

读者最常误解的点

把「漂移」读成「模型是错的」。漂移只是说两边现在不一致，方向可能是任意一边需要改。 比如 fact 一等化是代码走在前面、文本没跟上；而模型里那两个不存在的适配器，则是意图没有落地。 处置动作也因此不同：前者应更新文本，后者应决定是实现它还是从模型里删掉。

和上一章怎么衔接

第 9 章说的是「计划要变成什么」，这一章说的是「已经变了但文档没跟上的部分」。两者合起来， 就是这份现状描述与撰写模型之间的完整差额。

按角色的阅读路线

三条路线，各自只读该读的章节。

只想用 CLI 的人

  1. 先读开头「这个项目是什么」与「一个 task 的一生」，把 decision / task / fact 三个词分清。
  2. §2 只看图 2A 的前三层与图 2B：知道为什么写入要经过 daemon、为什么删缓存不会丢数据。
  3. §8 门禁：知道 done 为什么会被拒，以及拒了该补什么。
  4. 末尾术语表：遇到不认识的英文名回来查。

要改 daemon 的人

  1. §1 包与依赖方向：先确认你要动的东西在哪一层、允许 import 什么。
  2. §2 单写路与可重建读路：整章，尤其是冻结写计划与串行尾。
  3. §4 通用 action 契约：搞清你要改的分支是走通用路还是专用路。
  4. §5 或 §6（按你碰的管线选）与 §7 fleet：任何新写路都必须回答多节点问题。
  5. §9 Phase 6：确认你要加的东西是不是正好在被收敛的候选里。

要接一个新实体的人

  1. §3 实体身份与事件模式：先决定新实体属于 A / B / C 哪一类，绝大多数应该是 B 类。
  2. §4 通用 action 契约：走通用路，不要再造第五条专用分支。
  3. §6 任务包与文档写入：如果新实体有撰写文档，路由与写计划从这里抄。
  4. §8 门禁：新实体如果有承重状态迁移，就要在 manifest 里有对应的门。
  5. §10 权威收敛：把结论回写到架构模型，别只留在代码里。
