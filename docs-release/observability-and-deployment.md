# Observability, Reproducible Offline Builds, and Helm Deployment

This guide covers the generic operational baseline for running Harness Anything Center in Kubernetes or air-gapped enterprise environments with external PostgreSQL and external OIDC/Keycloak.

## Prometheus metrics and health probes

The daemon provides an opt-in, read-only HTTP server implemented on Node's built-in `node:http` with zero third-party telemetry dependencies. It is disabled by default so local developer daemons do not open TCP listeners.

Enable it via environment variables or CLI flags on `harness-anything-daemon serve`:

| Environment variable                  | CLI flag         | Default          | Purpose                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------- | ---------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HARNESS_DAEMON_METRICS_PORT`         | `--metrics-port` | unset (disabled) | TCP port (`0..65535`) for `/metrics`, `/healthz`, and `/readyz`                                                                                                                                                                                                                                                                         |
| `HARNESS_DAEMON_METRICS_BIND`         | `--metrics-bind` | `127.0.0.1`      | Bind host (`0.0.0.0` inside containers when scraped in-cluster)                                                                                                                                                                                                                                                                         |
| `HARNESS_DAEMON_METRICS_PATH`         | `--metrics-path` | `/metrics`       | Clean ASCII scrape path (`^/[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)*$`; rejects dot segments, non-ASCII, and reserved `/healthz` or `/readyz`)                                                                                                                                                                                                |
| `HARNESS_DAEMON_METRICS_BEARER_TOKEN` | —                | unset            | Optional Bearer token required on `/metrics` (fails closed when set to empty/whitespace; verified with constant-time digest comparison; responds with RFC 6750 `WWW-Authenticate: Bearer` on `401`)                                                                                                                                     |
| `HARNESS_DAEMON_METRICS_REQUIRE_AUTH` | —                | unset (`0`)      | When `1`/`true`, requires a non-empty `HARNESS_DAEMON_METRICS_BEARER_TOKEN` at startup and fails closed otherwise                                                                                                                                                                                                                       |
| `HARNESS_DAEMON_REQUIRE_IDENTITY`     | —                | unset (`0`)      | When `1`/`true`, `/readyz` returns `503` (`identity_not_configured`, `identity_verifying`, `identity_authority_sync_pending`, or `identity_unavailable`) until authoritative live OIDC/managed identity verification succeeds, and periodically re-verifies live credentials so upstream revocation transitions `/readyz` back to `503` |
| `HARNESS_STORAGE_BACKEND`             | —                | unset            | Optional strict backend enforcement (`postgres` or `sqlite`) checked inside daemon-host attach/register/init/update paths so `postgres` centers fail closed before writing or opening SQLite for any repository lacking a PostgreSQL entry                                                                                              |

### Endpoints

- `GET /metrics` (`HEAD` allowed): returns Prometheus exposition format (`text/plain; version=0.0.4; charset=utf-8`). All counters, gauges, histograms, and bounded-window latency quantiles are assembled strictly from resident in-memory host/writer state (`publishedStatus()`) with zero synchronous disk reads even on the very first cold scrape (package version is resolved eagerly at startup and sorted repository membership is maintained incrementally on attach/detach), zero ledger table scans, zero `registry.json` reads, and linear `O(R)` output formatting. Incoming request pathnames normalize RFC 3986 percent-encoded unreserved octets before route matching. When metrics are enabled, `ha_daemon_rpc_inflight` accounts for both local Unix JSON-RPC and Fleet TLS RPC requests via an independent Fleet counter so stalled Fleet deliveries never extend `build_superseded` drain beyond `fleetDrainDeadlineMs`.
- `GET /healthz`: process liveness probe; returns `200` (`live`) while the daemon process is running and `503` during shutdown or probe failure.
- `GET /readyz`: service readiness probe; returns `200` (`ready`) only when the daemon is live, initial attachments have settled, no repository is `warming`, `unavailable`, or reporting `projectionReadable === false` (`projections_unreadable`), any configured Fleet center listener restored cleanly, and (when `HARNESS_DAEMON_REQUIRE_IDENTITY=1`) authoritative live identity verification (including discovery and per-target `authoritySync.pending` tracking) has succeeded; otherwise returns `503` (`not_ready`) with machine-readable `reasons`.
- Collector or probe exceptions are isolated per request, recorded through the daemon diagnostics log, and answered with bounded `500` (`/metrics`) or `503` (`/healthz`, `/readyz`) responses without terminating the daemon.
- Non-`GET`/`HEAD` requests return `405 Method Not Allowed`; unknown routes return `404 Not Found`.

### Exposed metric families

- Process and build: `ha_daemon_up`, `ha_daemon_uptime_seconds`, `ha_daemon_build_info`, `ha_daemon_process_resident_memory_bytes`, `ha_daemon_process_heap_used_bytes`.
- Write queue depth: `ha_daemon_repos_loaded`, `ha_daemon_write_queue_depth`, `ha_daemon_write_queue_depth_total`.
- RPC counters and latency: `ha_daemon_rpc_requests_total`, `ha_daemon_rpc_inflight`, `ha_daemon_rpc_duration_seconds` (`_bucket`, `_sum`, `_count`), `ha_daemon_rpc_latency_quantile_seconds`.
- Runtime sessions: `ha_daemon_runtime_sessions_active`.
- Fleet center connections: `ha_daemon_fleet_center_enabled`, `ha_daemon_fleet_connections_active`, `ha_daemon_fleet_nodes_connected`, `ha_daemon_fleet_replication_streams_active`, `ha_daemon_fleet_deliveries_pending`.
- Projection lag: `ha_daemon_projection_watermark`, `ha_daemon_ledger_revision`, `ha_daemon_projection_lag_revisions`, `ha_daemon_projection_lag_revisions_max`.

## Reproducible offline build verification

`tools/reproducible-build.mjs` builds workspace deliverables from a pinned Git commit inside clean archive trees with `SOURCE_DATE_EPOCH` pinned to the commit timestamp, installs locked build-time `devDependencies` via `npm ci --offline --include=dev` in `--offline-cache` mode, verifies unified deliverable entries (regular files, normalized POSIX executable modes, and symbolic links) across `build-manifest.json`, output directories, and deterministic USTAR/gzip archives (`harness-anything/reproducible-build-manifest/v1`). `build --out` refuses protected paths, Git checkouts, existing non-empty directories that fail strict full-manifest verification (protecting unmanaged files and empty subdirectories), and `--archive` paths overlapping `--out` (including dot-prefixed filenames like `..archive.tar.gz` and symlinked parent directory aliases); `verify-manifest` walks delivered bundle directories strictly without skipping `node_modules` or `.git`.

```bash
# Build a deterministic bundle from a pre-seeded offline npm cache
node tools/reproducible-build.mjs build \
  --revision HEAD \
  --offline-cache /path/to/npm-cache \
  --out ./out/bundle \
  --archive ./out/bundle.tar.gz

# Run two independent clean builds against one pinned commit and verify bit-for-bit parity
node tools/reproducible-build.mjs verify \
  --revision HEAD \
  --mirror-node-modules \
  --verify-archive

# Verify an extracted bundle offline against its build-manifest.json (bytes, mode bits, symlinks)
node tools/reproducible-build.mjs verify-manifest \
  --bundle ./out/bundle
```

## Generic Helm Chart

The generic chart at [deploy/helm/harness-center/Chart.yaml](../deploy/helm/harness-center/Chart.yaml) targets external PostgreSQL (see [PostgreSQL daemon deployment](postgres-daemon.md)) and external OIDC/Keycloak (see [Server Daemon operations](operations-server-daemon.md)):

- **Single-authority topology & persistent workloads**: `replicaCount` is locked to `1` in both `values.schema.json` and render-time template checks (avoiding PostgreSQL writer fencing or split SQLite volumes). Persistent storage (`workloadKind: StatefulSet` or `Deployment` with `persistence.enabled: true`, the default) is required whenever `fleet.enabled: true` or `storage.backend: sqlite` so Pod replacement preserves `<userRoot>/fleet/state.json`, staged Fleet uploads/claims, `registry.json`, `rbac/`, and SQLite ledgers; purely stateless `Deployment` (`persistence.enabled: false`) is permitted only with `storage.backend: postgres` and `fleet.enabled: false`. `daemon.userRoot` mounts the `daemon-state` PVC root directly (preserving full in-place upgrade compatibility with pre-release PVC layouts) while `fleet.authorityRepoRoot` mounts `subPath: authority-repo` on the same PVC, and POSIX-normalized mount path collisions or nesting are rejected across schema, Helm render, and container entrypoint checks.
- **PostgreSQL & paired configuration enforcement (boot + runtime)**: when `storage.backend=postgres`, `storage.existingSecret` is mandatory, `start-center.sh` validates `<userRoot>/daemon-storage.json` against every enabled registered repository in `registry.json` (plus `fleet.authorityRepoId`) before launch with redacted parse diagnostics, and the daemon runtime enforces `HARNESS_STORAGE_BACKEND=postgres` on `daemon.repo.register`, `init`/bootstrap, `daemon.repo.update`, and repository attach so no runtime mutation can silently open local SQLite. Half-configured Fleet (`fleet.authorityRepoId` without `fleet.tlsExistingSecret` or vice versa) and half-configured external OIDC (`identity.issuerUrl` without `identity.existingClientSecret` or vice versa) are rejected at schema, render, and entrypoint boundaries.
- **External OIDC / Keycloak and Fleet TLS lifecycle (`start-center.sh`)**:
  - Reconciles `harness-daemon-registry/v2` and `fleet-center-config/v1` atomically on every start/upgrade when `fleet.enabled=true` with `fleet.authorityRepoId` and `fleet.tlsExistingSecret`, and removes stale persisted `center.json` when `fleet.enabled=false`.
  - On first boot with `identity.mode=external`, `identity.issuerUrl`, and `identity.existingClientSecret`, starts the daemon with `HARNESS_DAEMON_REQUIRE_IDENTITY=1` (keeping `/readyz` at `503` while `/healthz` passes), records a durable `.oidc-bootstrap-pending` marker before invoking `ha bootstrap --json --mode external --client-secret-stdin` via interruptible async waiting, requires a valid JSON receipt with `ok === true` and `authoritySync.pending !== true` (failing closed and retrying cleanly on restart if missing, malformed, `ok: false`, or `pending: true`), clears the marker only after verified completion, and hands off via `exec node` so the daemon runs directly as PID 1.
  - **Rotating or changing external OIDC / Keycloak configuration**: persisted `rbac/config.json` and `center-client-secret` drift causes `start-center.sh` to exit fail-closed before launching the daemon. Always rotate in order:
    1. Keep the existing Helm values / Secret (or run `helm rollback <release>` if an upgrade already triggered drift) so the Pod starts cleanly with its persisted OIDC authority.
    2. Exec into the **running** Pod, sign in as an administrator (`ha bootstrap --operation login`), and rotate the authority against its live daemon socket (`ha bootstrap --mode external --url <new-issuer> --realm <new-realm> --client-id <new-id> --client-secret-stdin`).
    3. Update the Kubernetes OIDC client Secret and run `helm upgrade` with matching `identity.*` values so future restarts match the rotated persisted state.
- **Separated, port-disjoint & RFC 1035 collision-resistant Service boundaries**: `service.yaml` (`<base>-fleet`) exposes only `fleet-tls` (`ClusterIP`/`NodePort`/`LoadBalancer`), `service-metrics.yaml` (`<base>-metrics`) always uses `ClusterIP` exclusively for the `metrics` port and is targeted by `ServiceMonitor` (`app.kubernetes.io/component: metrics`), and `service-headless.yaml` (`<base>-headless`, `clusterIP: None`) governs `StatefulSet` pod DNS. Render-time validation and `start-center.sh` reject overlapping `fleet.port` and `metrics.port` values when both are enabled. Default release base names sanitize dots/non-label characters, guarantee a leading ASCII letter (`ha-` prefix when a release begins with a digit), and embed a 16-character (64-bit) deterministic `sha256` discriminator of the raw `.Release.Name` (`<sanitized-prefix[:35]>-<sha16>`) plus explicit `-fleet` / `-metrics` / `-headless` / `-entrypoint` role suffixes so every valid Helm DNS-subdomain release (including `team.prod`, `team-prod`, `7center`, `prod`, `prod-harness-center`, and 53-char siblings) produces strict RFC 1035 DNS-label Service names (`<= 63` chars) with 64-bit collision resistance and `helm upgrade` stability (`fullnameOverride` is also validated against RFC 1035). Existing pre-release installations that mounted `daemon.userRoot` at PVC root can upgrade in-place by setting `fullnameOverride` to preserve existing PVC names and retain `registry.json`, `rbac/`, and `fleet/state.json` directly at PVC root (or perform a blue/green cutover and update external Service/PrometheusRule references to `<base>-fleet` / `<base>-metrics`). When `metrics.bearerTokenExistingSecret` is set, empty or whitespace-only Secret values fail closed at both entrypoint startup and daemon HTTP server initialization.
- **Release-scoped Prometheus Operator alerts**: `PrometheusRule` scopes all alerts (`HarnessDaemonDown`, `HarnessWriteQueueSaturated`, `HarnessProjectionLagHigh`, `HarnessRpcErrorRateHigh`) by `namespace` and the release's dedicated `service` label, preserves `(namespace, service)` grouping in `HarnessRpcErrorRateHigh` (`sum by (namespace, service)`), and attaches `release: <release-name>` to every alert rule's `labels:` so multiple releases firing simultaneously produce distinct alert identities.
